#   · AmqpConfig (config) — exchange, cola durable con x-dead-letter-exchange, DLX y DLQ.
#   · AvisoPublicador y ConsumidorDeAvisos (application) — productor e idempotencia.

# Los tests del enunciado del L11 (reloj, candado, asincronia, evento) se MOVIERON de enunciado/ a
# latidos/: dejaron de ser enunciado y pasaron a ser regresion. Ademas GANARON un contenedor de
# RabbitMQ: no porque su leccion cambiara —el evento sigue siendo AFTER_COMMIT y el envio sigue
# siendo asincrono— sino porque cambio POR DONDE sale el aviso. Es el precedente de "romper hacia
# atras" del Lab 07: el test heredado gana lo que necesita para seguir afirmando lo mismo.
#
# Archivos COMPARTIDOS que cambian a proposito:
#
#   compose.yaml
#     Entra RabbitMQ con tag fijado (rabbitmq:4.2.4-management, verificado vigente con
#     `docker manifest inspect`). Puerto AMQP efimero como el de Postgres; el de la consola fijo
#     (15672) para que la URL de la guia no cambie en cada arranque. Kafka NO se instala: se compara
#     conceptualmente en TEORIA.md (D-005).
compose.yaml
#
#   pom.xml
#     spring-boot-starter-amqp (gestionado por el BOM), testcontainers-rabbitmq, y el NUCLEO de
#     Resilience4j con version explicita — Resilience4j no esta en el BOM de Boot 4.1.0 (verificado,
#     count 0). Se usa el nucleo y no `resilience4j-spring-boot3` porque ese es el starter de BOOT 3:
#     su autoconfiguracion apunta a APIs que Boot 4 reorganizo. Y porque declarar el CircuitBreaker a
#     mano deja sus estados a la vista para que el test los afirme.
pom.xml
#
#   application.yml
#     El bloque spring.rabbitmq.listener: reintentos acotados y default-requeue-rejected=false, que

#     con el broker caido la DGT sigue atendiendo, asi que sacarla de rotacion tumbaria el servicio
#     entero por una dependencia de la que acabamos de desacoplarnos. Es la misma doctrina del
#     Lab 10 §5 aplicada a TESO, y esta explicada en TEORIA.md §8 — es contenido, no configuracion.
src/main/resources/application.yml
